# 建筑评分 BuildRate · 使用说明

> 自研活动制打分评审插件。一场活动里多座建筑，任意玩家给每座建筑打 1~10 分；**可反复改分记最新、打分公开可见、统计去掉最高/最低分、玩家自主报名**。Java / 基岩双端可用（箱子面板，基岩经 Geyser 自动转表单）。

## 一、管理员面板（推荐）

直接打开管理箱子菜单：

```
/br admin
```

面板内点按钮即可完成全部管理操作，不再依赖聊天栏文字：

| 按钮 | 作用 |
|---|---|
| 创建活动 | 关闭面板后在聊天栏输入活动名，自动创建并设为进行中 |
| 开启评分 | 把当前活动切到进行中，玩家可打分 |
| 截止并结算 | 结束当前活动，按名次把奖励发到获奖玩家邮箱 |
| 查看排名 | 箱子里按均分排名展示参评建筑（金锭图标） |
| 参与度 | 箱子里展示每位评委投了几票（玩家头图标） |
| 活动历史 | 箱子里列出历史活动（书本图标） |

列表面板点「返回管理面板」（箭头）回到主面板。

## 二、管理员：办一场评分活动

除面板外，也可用命令完成同样的事：

1. 创建活动（自动截止上一场进行中的活动）：
   ```
   /br create 2026国庆建筑大赛
   ```
   创建成功后会**全服聊天栏公告**该活动开启，引导玩家 `/br open` 打分、`/br join` 报名（管理面板里聊天创建同样会公告）。
2. 玩家自主报名，或管理员代报名：
   ```
   /br add 南瓜 南瓜城堡
   ```
3. 活动开始：`/br start`
4. 活动结束（**自动按名次结算发奖**）：`/br stop`
   `stop` 会按 config.yml 的 `rewards.ranks` 自动给前 N 名发奖，随后用管理面板「查看排名」或 `/br result` 核对。

> 已移除 `/br settle`：`/br stop` 即截止并自动结算，无需再单独手动结算。

## 三、玩家：报名 & 打分

| 指令 | 作用 |
|---|---|
| `/br join <建筑名>` | 报名参评（再报名=改名） |
| `/br open` | 打开打分面板：点建筑 → 选 1~10 分 |
| `/br score <编号> <分数>` | 命令直接打分（基岩兜底） |
| `/br list` | 参评列表（含当前均分/票数） |
| `/br result` | 排名（均分降序，去最高最低后） |

打分规则：
- 每人可给**每座建筑**打分一次，**可反复改分**，记录最新一次。
- **不能给自己的建筑打分**（可在 config.yml 开启 `allow-self-vote`）。
- 打分**公开可见**（`/br list` 显示每座建筑均分与票数，管理面板「参与度」看每个评分人投了几票）。

## 四、活动状态机（最容易踩坑的一节）

`events.status` 是**三态**，不是布尔：

| status | 含义 | 怎么进入 | 能被哪些命令看到 |
|:---:|---|---|---|
| `0` | **待开始**（已创建、未开启评分） | `/br create` 建活动时固定写入 0（`Db.createEvent` 显式 `VALUES(?,0,?)`，注意建表 `DEFAULT 1` 被这里覆盖） | `getOpenEvent` 集合（报名 / 列表 / 代报名 / start） |
| `1` | **进行中**（可打分） | `/br start` 置 1 | 两个集合都含它：既能报名也能打分、出结果、统计、结算 |
| `2` | **已截止**（不可再变动） | `/br stop` 置 2；或新建活动时 `UPDATE events SET status=2 WHERE status=1` **自动截止上一场进行中的活动** | 两个查询都取不到，只剩 `/br history` 与 `/br result` 的历史读 |

两个查询方法的分工决定了行为边界（`Db.java` 第 86–92 行）：

```sql
-- 报名 / 列表 / 代报名 / start 用（待开始也算"开放报名"）
SELECT * FROM events WHERE status IN (0,1) ORDER BY id DESC LIMIT 1   -- getOpenEvent()
-- 打分 / 结果 / 统计 / 结算 用（只认进行中）
SELECT * FROM events WHERE status = 1 ORDER BY id DESC LIMIT 1        -- getActiveEvent()
```

由此得到三条必须记住的结论：

1. **活动刚 `create` 完处于「待开始」，玩家可以先 `/br join` 报名，但 `/br score` 会回「当前没有进行中的活动」**——这是设计而非 bug，必须 `/br start` 后才开放打分。
2. **`/br create` 会自动截止上一场「进行中」的活动**（把 status=1 全部刷成 2）。所以想接着办下一场可以直接 create，但**上一场若还没 `/br stop` 结算，奖励不会发**——正确顺序是 `stop`（结算）→ 再 `create`。
3. **`getActiveEvent` 只取最新一场 status=1**（`ORDER BY id DESC LIMIT 1`），同时存在多个进行中活动只有最新那场生效；`settle` 完成后 status=2，`/br result` 仍按历史读该场，不会串到下一场。

> 代码注释已于 2026-11-19 订正：`storage/Models.java` 里 `Event` 的注释原写「status: 1=进行中 0=已截止」，与实际状态机不符（0 是待开始、2 才是已截止），现已改为三态说明并补上 `getOpenEvent(IN 0,1)` / `getActiveEvent(=1)` 的分工注释。`isActive()` 逻辑本来就没问题（判 `status == 1`），这次只动了注释文字，不影响字节码行为。

## 五、数据与统计口径

### 5.1 三张表（`plugins/BuildRate/data.db`，SQLite）

| 表 | 字段 | 要点 |
|---|---|---|
| `events` | `id INTEGER PK AUTOINCREMENT`, `name TEXT NOT NULL`, `status INTEGER NOT NULL DEFAULT 1`, `created_at INTEGER` | 一场活动一行；`status` 三态见 §四 |
| `builds` | `id PK`, `event_id`, `player`, `name`, `world`, `x`, `y`, `z` | 参评建筑；`one-build-per-player: true` 时每人每场仅一座；坐标在报名时记录玩家所在位置（作为展示/寻址参考） |
| `scores` | `event_id`, `build_id`, `voter`, `score`, `updated_at` | 一条 = 一人对一座建筑的当前分；`upsertScore` 覆盖旧值，故「可反复改分、只留最新」 |

连接按次开关，每次 `PRAGMA busy_timeout=5000` + `journal_mode=WAL`。**没有 `sqlite_sequence` 之外的额外表**（那是 SQLite 自增计数器）。

### 5.2 均分怎么算（`Stats.compute`）

| 票数 | `drop-highest-lowest: true` | `false` |
|---|---|---|
| `0` | avg = 0，min/max = 0 | 同左 |
| `1 – 2` | **按全部票平均**（否则会被扣光），`dropped=0` | 按全部票平均 |
| `≥ 3` | 扣 **1 个最高 + 1 个最低**，`denom = 票数 - 2`，`dropped=2` | 按全部票平均 |

- 排序：`avg` 降序 → `votes` 降序（`votes` 是**参与均分计算的有效票数**即 `denom`，原始票数在 `rawVotes` 里另存，界面可区分）。
- 自评拦截发生在**写入前**（见 §六打分链），不靠统计扣除。
- 同分并列不额外按时间打破平局，名次由排序结果直接决定，结算按名次取 `rewards.ranks` 的键。

> **实跑数据规模**（2026-11-19 读自有 `data.db`）：`events` 1 行、`builds` 10 行、`scores` 102 行——即历史上办过 1 场、10 座建筑参评、102 次有效打分记录。查库请只读，别手改。

## 六、打分的完整校验链

`score` 与面板点选走同一条链路，任一环节不过就返回对应提示（这是排查「打不了分」的顺序表）：

1. 必须是玩家（控制台不行）；
2. 参数齐备：`/br score <建筑编号> <分数>`；
3. `getActiveEvent()` 非空 → 否则「当前没有进行中的活动」（**待开始 status=0 也会走到这里**，见 §四）；
4. 编号是数字 → 否则提示 `/br list` 查编号；
5. 分数落在 `min-score ~ max-score`（默认 1~10）；
6. 建筑存在、`event_id` 属于当前活动、且 `ev.isActive()` → 否则「该建筑不属于当前活动或已截止」；
7. 非自评：建筑主人 == 打分者且 `allow-self-vote: false` → 「不能给自己的建筑打分」；
8. 全过 → `upsertScore(eventId, buildId, 玩家名, 分数)`。

## 七、结算奖励（全部发到邮箱，含南瓜币）

`/br stop` 截止活动时自动按 `config.yml` 的 `rewards.ranks` 结算。**所有奖励（南瓜币、物品）一律入队到玩家南瓜邮箱，由玩家 `/mailbox` 领取**。**只有真正获奖（配置了名次奖励）的在线玩家才会收到"请到邮箱领取"的私聊提示，未获奖玩家不打扰。** 第 N 名对应一份奖励列表，`type` 三种：

| type | 效果 | 说明 |
|---|---|---|
| `money` | 入队南瓜邮箱 | 玩家领取时由邮箱执行 `eco give` 加南瓜币，**南瓜账本来源记为该奖励描述（含活动名）** |
| `item` | 入队南瓜邮箱 | `data` 格式 `材质:数量`（如 `DIAMOND:1`） |
| `command` | 执行自定义命令 | `{player}` 替换为玩家名，仍直接控制台执行 |

邮箱里每条奖励的说明形如：`「活动名」第N名 · 第N名：500 南瓜币`。

示例：
```yaml
rewards:
  enabled: true
  announce: true
  ranks:
    "1":
      - { type: money, data: "500", desc: "第1名：500 南瓜币" }
      - { type: item, data: "DIAMOND:1", desc: "第1名：钻石 ×1" }
    "2":
      - { type: money, data: "300", desc: "第2名：300 南瓜币" }
    "3":
      - { type: money, data: "200", desc: "第3名：200 南瓜币" }
```

`announce` 为 true 时结算会广播前 3 名。

**账本联动**：需要南瓜账本 MoneyLedger 在服上运行。玩家在 `/mailbox` 领取南瓜币后，南瓜账本里这笔记录的**来源名就是含活动名的奖励描述**（如「2026国庆建筑大赛」第1名 · 第1名：500 南瓜币），便于在 `/moneyledger` 里按活动名追溯每一笔发币。

## 八、命令与权限（14 个子命令全表）

`/br`（别名 `/buildrate`）分支共 **14 个**，逐一来自 `BuildRateCommand` 的 switch：

| 子命令 | 需 `buildrate.admin` | 仅玩家 | 取活动用 | 说明 |
|---|:---:|:---:|---|---|
| `/br admin` | ✅ | ✅ 箱子界面 | — | 打开管理面板（§一） |
| `/br create <名称>` | ✅ | 否 | `getOpenEvent`（用于截止旧场） | 建活动，status=0「待开始」；名字留空默认「建筑大赛」；**会顺带把上一场进行中的活动置 2**（见 §四） + 全服公告引导报名 |
| `/br start` | ✅ | 否 | `getOpenEvent` | 置 status=1 开启评分 + 全服公告 |
| `/br stop` | ✅ | 否 | `getActiveEvent` | 置 status=2 截止 **+ 按名次自动结算发奖**（§七） |
| `/br add <玩家> <建筑名>` | ✅ | 否 | `getOpenEvent` | 管理员代报名 |
| `/br remove <编号>` | ✅ | 否 | — | 移除参评建筑及其全部评分 |
| `/br stats` | ✅ | 否 | `getActiveEvent` | 参与度统计：**文档旧版漏列了这一条**，看每位评委投了几票（面板「参与度」同数据） |
| `/br join <建筑名>` | ❌ | ✅ 需定位 | `getOpenEvent` | 玩家自助报名，再报名 = 改名 |
| `/br open` | ❌ | ✅ 箱子界面 | — | 打分面板：点建筑 → 选 1~10 分 |
| `/br score <编号> <分数>` | ❌ | ✅ | `getActiveEvent` | 命令直接打分（基岩兜底），校验链见 §六 |
| `/br list` | ❌ | 否 | `getOpenEvent` | 参评列表（均分 / 票数） |
| `/br result` | ❌ | 否 | `getActiveEvent` | 当前活动排名（去最高最低后均分降序） |
| `/br history` | ❌ | 否 | 全部 | 历史活动列表（含已截止 status=2） |
| `/br help` | ❌ | 否 | — | 用法说明；**未识别的子命令也会落到 help**（default 分支） |

两点务必注意：

- **`plugin.yml` 的 `usage` 已于 2026-11-19 补齐**：原串只写 12 个子命令，漏了 `admin` 与 `help`（代码本来就支持，只是元数据没写全）；现已改为 `create|list|join|add|remove|start|stop|admin|open|score|result|stats|history|help` 共 14 个，与 switch 分支一一对应。⚠️ 这是 **源码侧**改动，`target/BuildRate-1.0.0.jar` 与实跑 jar 内嵌的 `plugin.yml` 仍是旧的 12 个——usage 只影响错误提示文案，不换 jar 也没有功能影响；下次重打包时会自动带上。
- `buildrate.admin` 的 `default: op`，非 op 玩家组需显式授权才能用上面打 ✅ 的 7 个命令（本服 LuckPerms 为显式授权模式）：

```
/lp group admin permission set buildrate.admin true
```

Tab 补全只做了一件事：`/br score <TAB>` 补在线玩家名相关参数（`args.length==2/3` 且首参为 `score`），其余子命令不补全。

## 九、配置（config.yml）

`plugins/BuildRate/config.yml`，两节：

```yaml
scoring:
  min-score: 1                  # 打分下限
  max-score: 10                 # 打分上限
  drop-highest-lowest: true     # 票数 ≥3 时去掉 1 高 1 低再算均值（§5.2）
  allow-self-vote: false        # false = 禁止给自己的建筑打分
  one-build-per-player: true    # 每人每场只允许一座参评建筑

rewards:
  enabled: true                 # false 时 /br stop 只截止不发奖
  announce: true                # 结算时广播前 3 名
  participation:                # 参与奖（默认关闭）
    enabled: false
    amount: 50                  # 南瓜币数额
    exclude-top: 5              # 前 5 名拿名次奖，不再领参与奖
  ranks:                        # 名次 → 奖励列表（可一条名次给多份）
    "1":
      - { type: money, data: "500", desc: "第1名：500 南瓜币" }
      - { type: item,  data: "DIAMOND:1", desc: "第1名：钻石 ×1" }
    "2": [ { type: money, data: "300", desc: "第2名：300 南瓜币" } ]
    "3": [ { type: money, data: "200", desc: "第3名：200 南瓜币" } ]
    "4": [ { type: money, data: "100", desc: "第4名：100 南瓜币" } ]
    "5": [ { type: money, data:  "50", desc: "第5名：50 南瓜币"  } ]
```

**没有 reload 命令**：改 `config.yml` 后需重启服务端才生效（所有取值都在 `BuildRate` 的 getter 里即时读 `getConfig()`，但没地方触发重载）。实跑服上那份 `config.yml` 与源码出厂版本**键结构完全一致**（已比对，无缺失键）。

## 十、依赖、部署与构建

### 10.1 依赖（**本节纠正旧文档的错误陈述**）

| 依赖 | `plugin.yml` 声明 | 实际作用 | 缺失后果 |
|---|---|---|---|
| **SQLite JDBC** | 不声明，也**没有打进 jar** | `data.db` 读写 | 由 Leaf 服务端 `libraries/` 提供——实测该目录已有 `sqlite-jdbc-3.46.1.3` / `3.47.0.0` / `3.49.1.0`。**旧文档写「内置 sqlite-jdbc（已打进 jar）」不属实**：`BuildRate-1.0.0.jar` 只有 16 个条目（15 个 class/resource + MANIFEST），`org/sqlite/*` 为 0，也没有 `META-INF/services/java.sql.Driver` |
| **PumpkinMail**（软依赖） | 是（`softdepend`） | `money` / `item` 类名次奖与参与奖改为投递玩家邮箱 | 未装则发奖环节拿不到邮箱 API，名次奖发不出去（南瓜币/物品不会到账） |
| **Essentials**（软依赖） | 是（`softdepend`） | 在线玩家离线的 `eco give` 兜底与余额操作 | 未装时 `eco give` 命令发奖会失败 |
| **MoneyLedger** | **不声明**（无直接依赖） | 南瓜邮箱领取时经邮箱写账本，本活动来源名即「活动名+名次」描述 | 未装只是账本里少了来源，发奖照常 |

> 换句话说：**发币链路真正依赖的是 PumpkinMail + EssentialsX，MoneyLedger 属于「装了更好」的可观测层**。这与旧文档「（三者）同服运行即可」的并列表述不同。

### 10.2 部署

1. 把 `target/BuildRate-1.0.0.jar` 复制到服务端 `plugins/`；
2. **停服后完整重启**，不要用 `/reload` 换 jar（`自研/README.md` §四通则）；
3. 首次启动生成 `plugins/BuildRate/config.yml`，填好 `rewards.ranks` 再办活动；
4. 实跑状态：主服 `plugins/BuildRate-1.0.0.jar` 与源码同为 1.0.0，`data.db` 已有 1 场活动 / 10 座建筑 / 102 条评分的历史数据。

### 10.3 构建

按仓库总则用 **JDK 25 `javac --release 21`**；`softdepend` 插件用 `自研/lib/` 下的 jar 做编译期类型解析（`PumpkinMail.jar`、`EssentialsX.jar`、`leaf-api-26.3.build.13-alpha.jar`），classpath 还需 `adventure-api` 与 `annotations` 两个传递依赖。`pom.xml` 供 IDE 与依赖声明，**无 `build.py`**，产物看 `target/`。

```

├─ pom.xml
```
