# MoneyLedger —— 南瓜账本（自研）

> 全服南瓜币（EssentialsX 余额）的**权威流水账**：每一笔余额变动都留痕，事件链路漏掉的用 EssentialsX 自己的 `trade.log` 幂等补齐，并且能对账、能体检、能导出。

| 项             | 值                                                                          |
| -------------- | --------------------------------------------------------------------------- |
| 插件名         | `MoneyLedger`（对外称**南瓜账本**）                                          |
| 版本           | `1.1.0`（`plugin.yml`）                                                     |
| 主类           | `com.nangua.moneyledger.MoneyLedger`                                        |
| 包名           | `com.nangua.moneyledger`                                                     |
| `api-version`  | `26.3`（Leaf 26.3）                                                          |
| 命令 / 别名    | `/moneyledger` / `moneylog`                                                  |
| 权限           | `moneyledger.admin`（默认 `op`，**所有子命令都需要**）                        |
| 数据文件       | `plugins/MoneyLedger/ledger.db`（SQLite）、`ledger-failed.log`、`export/*.csv` |
| 权威补充源     | `plugins/Essentials/trade.log`（EssentialsX 自写流水，只读）                  |
| 运行时依赖     | EssentialsX（`UserBalanceUpdateEvent` + `trade.log` + `userdata`）、SQLite JDBC |
| 被谁调用       | PumpkinMail 通过反射调 `MoneyLedger.setReason(...)` 写入来源备注               |
| 实跑位置       | 主服 `leaf-26.3-多服/plugins/MoneyLedger-1.1.0.jar`                           |

## 一、为什么做这个

服里的南瓜币会经由十几个插件流转（每日收购、飞行、领地、任务、邮箱、离线奖励、快捷菜单、周税……），一旦出现「玩家说钱少了」「活动奖励到底发没发」这类争议，靠 EssentialsX 的 `balance` 只能看到一个**当下的数**，看不到**过程**。

最初的账本只挂 `UserBalanceUpdateEvent`，看起来是对的，但实测翻车：**2026-10-30 ~ 11-08 期间 `ledger.db` 一条记录都没写进去**，而同期 `trade.log` 里有 5000+ 笔真实变动。原因是事件链路在某些调用路径（尤其控制台/API 直接改余额）不触发，加上写库异常被空 `catch` 吞掉，账本静默变哑。

所以 1.1.0 的思路改成两条腿：

1. **事件实时直记**——在事件线程内同步落盘，不再排队，崩溃/关服不丢；
2. **`trade.log` 幂等回填**——拿 EssentialsX 自己写的权威流水做第二数据源，定期补齐事件漏掉的笔数。

两条腿交叉的结果就是：**可以做到「所有变动都有记录」，而且能对账验证是否真的所有都有**。方块不骗人，账本也不能骗人。

## 二、一笔流水里存了什么

`ledger` 表每行 = 一笔余额变动。字段分四组：

**① 身份与时间**

| 字段   | 说明                                                             |
| ------ | ---------------------------------------------------------------- |
| `uuid` | 玩家真实 UUID                                                     |
| `name` | 玩家名（解析顺序见 §四.3）                                        |
| `time` | 毫秒时间戳；统计与对账一律按 `Asia/Shanghai` 切自然日             |

**② 金额（双份）**

| 字段                        | 说明                                       |
| --------------------------- | ------------------------------------------ |
| `old_balance` / `new_balance` / `delta` | double，用于 SQL 聚合、余额链校验 |
| `old_exact` / `new_exact` / `delta_exact` | **BigDecimal 精确文本**，展示与导出优先用它 |

为什么要双份：double 存货币会出现 `0.18000000000000682` 这种脏尾巴。1.1.0 起金额同时以 `toPlainString()` 文本落库，**给人看的永远是精确值**，给 SQL 聚合用的保持兼容。所有展示入口（`recent` / `summary` / CSV）都走 `displayDelta()` 之类的方法优先取精确文本。

**③ 归因**

| 字段       | 说明                                                        |
| ---------- | ----------------------------------------------------------- |
| `cause`    | EssentialsX 给的 `UserBalanceUpdateEvent.Cause` 枚举名        |
| `category` | 本插件的类别（§三.1，16 类）                                 |
| `source`   | 人类可读来源，由三段拼接：`插件名 / 类.方法(L行号)` ＋（可选）命令上下文 ＋（可选）发奖方备注，规则见 §三 |

**④ 可靠性**

| 字段          | 说明                                                                      |
| ------------- | ------------------------------------------------------------------------- |
| `origin`      | 记录怎么来的：`EVENT` 事件直记 / `BACKFILL` 日志补记 / `FAIL_REPLAY` 失败重放 |
| `dedup_base`  | 幂等基键 = `玩家小写 + 秒 + 金额(2位) + 变动后余额(2位)`                      |
| `dedup_key`   | `dedup_base` +（同基键第 n 次时追加 `#n`），**唯一索引**                      |

去重键是回填能反复跑的前提：同一笔变动无论从事件还是从 `trade.log` 再算一遍，基键都一样，不会插出第二条。历史上确实存在「同一秒同一金额」的多笔（例如一次 `/pay` 拆两笔、或同毫秒并发），按出现顺序编号 `#2`/`#3` 让它们都能入库，同时保证唯一约束不炸。

索引：`idx_name`、`idx_cat`、`idx_time`、`idx_uuid`、`idx_dedup_base`、`idx_dedup_key`（UNIQUE）。库连接开 `PRAGMA journal_mode=WAL`、`synchronous=NORMAL`、`busy_timeout=5000`。

## 三、来源是怎么被判定的

### 3.1 类别表（`Category`）

中文名可用于 `/moneyledger recent <玩家> <中文类别>` 过滤（`fromName` 英文名和中文标签都认）。枚举**只追加不改顺序**，库里存的是 `name()`，历史数据不受影响。

| 枚举               | 中文标签   | 典型来源                          |
| ------------------ | ---------- | --------------------------------- |
| `TRANSFER`         | 转账       | `/pay`（Cause=COMMAND_PAY）        |
| `SHOP`             | 买卖       | EconomyShop                        |
| `AUCTION`          | 拍卖       | AuctionHouse                       |
| `BUYOUT`           | 每日收购   | DailySell                          |
| `TAX`              | 周税       | EzTax                              |
| `QUEST`            | 任务       | Quests                             |
| `ACTIVITY`         | 活动/管理  | PumpkinMail、OfflineReward、QuickMenu、`/eco give` |
| `ACTIVITY_VOTE`    | 活动参与   | BuildRate                          |
| `SELL`             | 出售       | Cause=COMMAND_SELL                 |
| `SPECIAL`          | 特殊       | Cause=SPECIAL                      |
| `OTHER`            | 其他       | EssentialsX 及其他未识别           |
| `UNKNOWN`          | 未知       | Cause 为 null 或未落入映射          |
| `FLIGHT`           | 飞行消费   | PumpkinFly                         |
| `RESIDENCE`        | 领地       | Residence                          |
| `BACKFILL`         | 日志回填   | 由 `trade.log` 补记的记录           |
| `ADJUST`           | 余额校正   | 人工/校正写入                       |

`FLIGHT` / `RESIDENCE` / `BACKFILL` / `ADJUST` 是 1.1.0 新增的四个。

### 3.2 调用栈扫描（`SourceDetector`）

Cause 只能区分「命令 / API / 特殊」，要精确到**哪个插件发的钱**得看调用栈。1.1.0 把这里重写了一遍（诊断依据：本地 `ledger.db` 18240 条实测）：

- **旧实现取「第一个非忽略帧」**，结果命令发放时抓到的是 Brigadier 的 `context` / `ContextChain.runExecutable`，Vault、Residence 桥也一样——记下来的是命令框架，不是真实发奖方。
- **新实现扫描整个调用栈**，优先命中已知插件规则表；框架、桥、命令调度器一律跳过（`IGNORE` 列表含 `org.bukkit` / `io.papermc` / `net.ess3` / `com.earth2me.essentials` / `net.milkbowl.vault` / `com.mojang.brigadier` / JDK 与常见库前缀等）。
- **补上本服插件的真实包名**：`com.hh.dailysell`、`com.nangua.pumpkinfly`、`com.nangua.pumpkinmail`、`com.nangua.offlinereward`、`com.nangua.quickmenu`、`com.nangua.buildrate`、`com.bekvon.bukkit.residence`。
- **修掉失效映射**：Quests 5.3.2 包名已从 `com.leonardobishop.quests` 迁到 `me.pikamug.quests`，旧表完全没有新包名，任务奖励全被记成 `OTHER`——现在两条都在规则表里，`me.pikamug.quests` 排前面。
- 一笔事件只扫一次栈：`detect()` 的结果同时用于定类别和生成来源描述，不再重复扫。

规则表**顺序即优先级**，命中第一条就返回。新增自研插件想被精确识别，就在 `SourceDetector.RULES` 里加一行 `{包名前缀, 友好名, 类别}` 重新编译。

### 3.3 跨插件来源备注 `setReason`

`MoneyLedger.setReason(String)` 是 `public static`、**ThreadLocal** 的：发奖方在扣钱前设一句备注，同一线程内的下一笔余额变动会把这句写进 `source`。

- 传 `null` 或空串 = **清除**。这是 1.1.0 修的 bug：旧版清除不掉，上一笔的备注会串到下一笔，直接污染归因。
- 调用方通过反射使用（`Class.forName("com.nangua.moneyledger.MoneyLedger")`），**账本没装也不会报错**，保持松耦合。
-  PumpkinMail 就是用它把「建筑大赛第 1 名：500 南瓜币」这类活动描述打进来源，玩家那笔南瓜币因此在账本里带着活动名。

### 3.4 命令上下文

另外挂了两个 MONITOR 监听：`PlayerCommandPreprocessEvent`（玩家发的指令）与 `ServerCommandEvent`（控制台发的），把 `执行者: 指令原文` 记进 ThreadLocal。

下一笔余额变动若在同一线程、且在 TTL 内发生，就追加 `| 命令: ...`。默认 `command-context-ttl-seconds: 5`——**超时即丢弃**，避免 5 秒前打的指令串到后面不相干的一笔上。

## 四、写入路径上的三道保险

### 4.1 同步落盘（不再用内存队列）

每笔变动在事件线程内直接 `INSERT`。WAL + `synchronous=NORMAL` 下单条约 0.1ms，换来的是「进程崩溃、`/stop`、调度器异常都丢不了记录」。旧版攒批队列一旦被绕过就是一整段空白。

`delta == 0` 的变动直接不记（老新余额相等没必要留一条噪音）。

### 4.2 失败转存 + 启动重放

写库失败不再被空 `catch` 吞掉：会 `severe` 打日志，同时把这一笔按 `time\tnew-old\tdelta\t字段(Base64)...` 追加到 `ledger-failed.log`。Base64 是为了让备注/来源里的中文、逗号、制表符都不破坏行结构。

下次 `open()` 时自动重放该文件：成功的写入（`origin` 保留原值并生成去重键），失败的留在文件里下次再试，并在日志里给出「成功 N / 失败 M」。

### 4.3 玩家名解析

基岩玩家（Floodgate 前缀名）和离线场景下，`e.getPlayer().getName()` 有时只给回一个 8 位十六进制的 UUID 前缀。解析顺序：

1. 事件返回的名字非空、且**不像 UUID 前 8 位**（`[0-9a-fA-F]{8}`）→ 直接用；
2. 否则读 `plugins/Essentials/userdata/<uuid>.yml`，取 `last-account-name:`；
3. 否则 `Bukkit.getOfflinePlayer(uuid).getName()`；
4. 都拿不到才退回 `uuid` 前 8 位（这种记录会被 `verify` 计入「名称兜底」项）。

## 五、`trade.log` 幂等回填（1.1.0 新增）

### 5.1 处理哪三类行

| 日志行            | 怎么解读                                                          |
| ----------------- | ----------------------------------------------------------------- |
| `API,Add`/`API,Subtract` | 字段 5 = 金额，末尾字段 = 变动后余额；`old = new - delta` |
| `Command,Pay`     | **一行代表两笔**（付款人 + 收款人），字段 4/8 是双方名、字段 5 是金额；用它前面紧邻的两条 `Update,Set` 行分别还原双方变动后余额，配对成两笔准确记录 |
| `Update,Set` / `API,Set` | **伴随行，不计为独立变动**                                 |

日志时间用中文日期正则解析（`YYYY年M月D日 ... HH:MM:SS`），时区 `Asia/Shanghai`。

### 5.2 为什么「伴随 Set 行」不补

`Set` 行只写入变动后的余额，没有变动前余额，算不出 `delta`。这类在运行期其实已经被事件链路直记过了，所以不自动补；`verify` 会单独给出「独占 Set 行 N 笔」让你知道有多少这种情况，不假装是缺口。

### 5.3 幂等与进度

- 进度以**已处理行数**存在 `backfill_state` 表；文件最后一行如果不完整就留到下次重读，避免截断行被误算。
- 每笔先算 `dedup_base`，查账本已有 M 条，只补第 M+1..N 条 → **反复跑不会多插**。
- 性能：回填批量写前一次性 `baseCounts()` 把所有基键的已有条数载入内存，随插随增，避免上万次逐条 `SELECT COUNT(*)`。整批走一个事务，失败则逐条重试。
- 补记的记录固定为 `category=BACKFILL`、`origin=BACKFILL`、`source=Essentials/trade.log`——**不臆测是哪个插件触发的**，宁可标得保守。

### 5.4 触发时机

启动时异步跑一次，之后按 `backfill.interval-minutes`（默认 15）**全部在异步线程**执行，不占用主线程 TPS。也可手动 `/moneyledger backfill`。

## 六、配置

`plugins/MoneyLedger/config.yml`（源码基线：`src/main/resources/config.yml`）

```yaml
query-limit: 30                     # /recent 默认返回条数
command-context-ttl-seconds: 5      # 命令上下文有效期，超时不追记到本笔

backfill:
  enabled: true                     # 关掉就没有任何自动补记了，只留事件链路
  interval-minutes: 15              # 周期回填间隔（最小按 1 处理）
  min-date: ""                      # 只补该日期(含)之后，格式 YYYY-MM-DD；留空 = 连启用前的历史一起补
```

1.1.0 起这些行为**固定写死、不再有开关**，注释里也标明了：同步落盘、失败转存重放、BigDecimal 精确金额、全部子命令需 `moneyledger.admin`、`verify` 输出对账 + 体检报告。

改完配置需要 `/reload plugin` 或重启才生效（本插件未提供 `/moneyledger reload`）。

## 七、命令手册

**全部子命令都需要 `moneyledger.admin`（默认 op），玩家无入口。**

| 指令                                        | 作用                                                                 |
| ------------------------------------------- | -------------------------------------------------------------------- |
| `/moneyledger`                              | 打印用法                                                             |
| `/moneyledger recent <玩家> [类别]`          | 按时间倒序看流水；类别支持中 / 英文；`[日志补记]` 标签标出 BACKFILL 笔 |
| `/moneyledger summary <玩家>`                | 按类别汇总净额（正绿负红，两位小数）                                   |
| `/moneyledger export [玩家]`                 | 导出 CSV 到 `plugins/MoneyLedger/export/`，不带玩家 = 全量            |
| `/moneyledger stats`                        | 总笔数 + 按 `origin` 分布（事件实时 / trade.log 补记 / 失败重放）      |
| `/moneyledger backfill [full]`              | 手动幂等回填；`full` = 从第 0 行重扫（靠去重保证不多插）               |
| `/moneyledger verify`                        | 与 `trade.log` 逐日对账 + 数据质量体检，异步执行                      |

别名 `$moneylog`。Tab 补全：一级子命令；`recent` 第三参数补类别；`backfill` 第二参数补 `full`。

`recent` 输出格式：

```
06-12 21:04:31 [每日收购] +50 余额 1230 (DailySell / BuyoutMenu.click(L118) | 命令: 玩家: /sell 64 diamond)
```

### CSV 列（13 列）

`time,uuid,name,category,cause,source,origin,delta,delta_exact,old_balance,old_exact,new_balance,new_exact`

`source` 里的逗号/换行会做转义（换行拍平成空格，含逗号或引号的字段整体加引号），不会被备注文本破坏分列。

## 八、`verify` 体检报告读法

这是账本的**自证清白**工具，输出分四块：

1. **规模**：总笔数 + 各 `origin` 分布。
2. **字段质量**：`delta ≠ new-old`（>0.005 才算）、`delta = 0`、名称/来源为空、去重键为空、无精确金额（1.1.0 之前的历史 EVENT 行属正常）、UUID 缺失（事件与补记分开计）、名称兜底为 UUID 前 8 位的条数。
3. **与 `trade.log` 逐日对账**：只列**日志笔数 > 账本笔数**的日子并给出缺口；反过来账本多于日志不计缺口——因为 `/eco give` 这类事件直记在日志里没有对应变动行，属正常，会以「账本多出 X 笔」单列说明。账本启用之前的日志日期会被自动剔除，不冤枉历史。
4. **余额链连续性**：按 uuid（缺失则按名字）把每笔串起来，`上一笔 new_balance` ≠ `本笔 old_balance`（容差 0.01）就计一处断裂，并给最多 3 个样例（玩家 @ 日期 前值→后值）。直接 `setMoney`、同毫秒并发、启用前漏记都可能导致断裂，属线索不是定性。
   另外单列「独占 Set 行 N 笔」（见 §5.2）。

用法建议：先 `backfill full` 再 `verify`，缺口应显著收敛；剩下的再看余额链，逐条判断是不是人为 `setMoney`。

## 十、构建

**编译口径**（与 `自研/README.md` 一致）：JDK 25 的 `javac --release 21`，产物保持 Java 21 字节码才能被服务端加载。

```bash
# classpath = ../lib/leaf-api-26.3.build.13-alpha.jar;../lib/EssentialsX.jar;<adventure-api>;<annotations>;sqlite-jdbc
javac --release 21 -encoding UTF-8 -d out $(find src/main/java -name '*.java')
```

- `pom.xml` 依赖全部 `provided`：`leaf-api 26.3.build.13-alpha`（`systemPath` 指向 `../lib/`）、`EssentialsX 2.22.1`（`../lib/EssentialsX.jar`）、`sqlite-jdbc 3.53.4.0`、`adventure-api 5.2.0`、`annotations 23.0.0`。systemPath 依赖不带传递依赖，所以后两个显式声明。
- SQLite JDBC 运行时由服务端 `libraries/` 提供（本插件也自带 `sqlite-jdbc-3.53.4.0.jar`，编译与运行都依赖）。
- 无 `build.py`，日常部署以 `target/` 内已编译 jar 为准，`pom.xml` 主要服务于 IDE 补全与依赖声明。

**版本一致性（2026-11-19 已校正）**：`pom.xml` 的 `<version>` 原来是 `1.0.0`，与 `plugin.yml` / 实跑 jar 的 `1.1.0` 不符——那样走 Maven 打包会产出 `moneyledger-1.0.0.jar`，与 `target/` 里的历史旧包撞名、也与部署习惯不符，**现已同步为 `1.1.0`**。另外实测本插件三处产物（根目录 jar、`target/MoneyLedger-1.1.0.jar`、主服 `plugins/MoneyLedger-1.1.0.jar`）内嵌版本均为 `1.1.0`、**class major 65（Java 21）**，源码—产物—实跑完全对齐，不需要重新部署。（`target/` 里另留有一份 11-06 的 `MoneyLedger-1.0.0.jar` 作历史对照，部署时别拿错。）

## 十一、部署与运维要点

1. **必须先有 EssentialsX**。没有它就没有 `UserBalanceUpdateEvent`，也没有 `trade.log`，账本变成空壳（不会崩，但也记不到东西）。
2. **确认 EssentialsX 开着交易日志**——`trade.log` 是回填的命脉。日志不存在时 `Result` 会直接回报 `trade.log 不存在: <路径>`，此时只有事件链路那一半保障。
3. **升级 1.1.0 会自动做一次旧库迁移**：`ALTER` 加 6 个新列（SQLite 不支持 `ADD COLUMN IF NOT EXISTS`，靠 `PRAGMA table_info` 判断），建索引，把空 `origin` 统一填成 `EVENT`，并给历史记录补去重键（同基键按顺序 `#2`/`#3`）。原字段一条都不改写。日志里会看到「旧库加列: xxx」「历史 N 条已补去重键」。
4. **首次上线建议跑一次 `/moneyledger backfill full`** 把启用前的历史一次性拉平，再 `verify` 看缺口。之后交给 15 分钟周期。
5. **别手改 `ledger.db`**。所有金额展示走精确文本列，若外部工具重算 `delta` 会因 `origin`/`source` 与去重键错位而污染对账结论。真要清洗，改完记下改动，方便下次 `verify` 解释缺口。
6. 数据文件属于插件运行数据，**汉化/整理配置时不要动 `ledger.db`、`ledger-failed.log`、`export/`**（与仓库既有约定一致）。

## 十二、常见问题

| 现象                              | 定位                                                              |
| --------------------------------- | ----------------------------------------------------------------- |
| 账本一条都没有，但玩家余额在动    | 先确认 EssentialsX 在；再看 `verify` 的日志缺口；`backfill full` 补 |
| 某笔来源显示 `EssentialsX/外部调用` | 调用栈没命中规则表（新插件/改包名），往 `RULES` 加一行重编译       |
| 来源出现 `Brigadier` 之类框架名   | 1.1.0 已修；若还在，检查是否跑的是旧 jar                          |
| 备注串到了下一笔                  | 1.1.0 已修 `setReason(null)` 清除逻辑；调用方务必成对 set/clear     |
| 金额显示一长串小数                | 1.1.0 前的历史 EVENT 行没有精确文本列，`verify` 会单列计数          |
| 同一次发奖出现两笔相同记录        | 事件与日志都写了？检查 `dedup_key` 唯一索引是否建立成功、「余额链」是否报错 |
| 日志反复出现「失败记录重放: 成功 0 / 失败 N」 | `ledger.db` 被占用或磁盘/权限问题，先解占用，文件不会丢        |
