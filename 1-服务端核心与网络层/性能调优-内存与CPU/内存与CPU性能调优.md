# 性能调优 — 内存与 CPU

本分类记录 MC 服务端性能核心概念：堆内/堆外分工、Xms/Xmx、CPU 单线程 tick 瓶颈、容量量级与判断方法。适用于本机 Leaf 26.3 多服（survival / minigames / skyblock + Velocity）。

## 1. 核心结论

| 项       | 内容                                                           |
| -------- | -------------------------------------------------------------- |
| 性能瓶颈 | CPU 主线程 tick（20 TPS，实体 AI / 红石 / 区块加载都在主线程） |
| 堆的作用 | 只负责"装得下"当前对象，加大堆不会让 tick 变快                 |
| OOM 真因 | 多数是堆外（native memory）被吃光，不是堆不够                  |
| 优化顺序 | 先减实体/降视距（CPU 侧），再谈堆大小                          |

## 2. 内存结构

| 区域           | 由谁控制        | 装什么                                                                    |
| -------------- | --------------- | ------------------------------------------------------------------------- |
| 堆内（Heap）   | `-Xmx` / `-Xms` | 加载的区块、实体、玩家、箱子物品、村民、红石状态                          |
| 堆外（Native） | Xmx 管不着      | 线程栈、JIT 编译缓存、网络缓冲、**插件的原生缓存（如 BlueMap 生成地图）** |

CPU 是"脑子"（每秒算 20 次 tick），内存是"桌面"（摊开当前要处理的东西）。桌子大 = 能摊更多，**不是算得更快**。

### OOM 报错判读

```
There is insufficient memory for the Java Runtime Environment to continue.
Native memory allocation (malloc) failed ... Error detail: Chunk::new
```

- `Native` = 堆外分配失败，JVM 连几 MB 都申请不到 → 进程被杀
- 加大 Xmx **只会挤占堆外**，让这类崩溃更容易发生
- 排查看 `hs_err_pid*.log`，别看代理日志（代理看不到后端崩溃）

## 3. Xms / Xmx

| 参数              | 含义                                               |
| ----------------- | -------------------------------------------------- |
| `-Xms4G`          | 启动初始堆 4G                                      |
| `-Xmx16G`         | 最大堆 16G，JVM 按需在 4~16G 之间伸缩 = **动态堆** |
| `-Xms10G -Xmx10G` | 两者相等 = **固定堆**，容量恒定不伸缩              |

### 固定堆 vs 动态堆

| 对比     | 动态堆（Xms≠Xmx）               | 固定堆（Xms=Xmx）    |
| -------- | ------------------------------- | -------------------- |
| 容量     | 随负载伸缩                      | 恒定                 |
| GC       | 伸缩有开销，堆波动易触发额外 GC | 稳定                 |
| 卡顿     | 涨堆时可能抖动                  | 更平滑               |
| 内存占用 | 平时省一点                      | 启动时占满设定值     |
| 风险     | 上限设太高，真涨上去会 OOM      | 上限锁死，天然防 OOM |

MC 服务端长期运行，主流建议（含 Aikar's flags）是 **Xms = Xmx**。动态堆的"平时省内存"对服务端意义不大，反而上限虚高风险更大。

## 4. 32G 机器的内存分配

四 JVM 同机，survival 不能独占：

| survival 堆 | survival 总占（含堆外） | 4 服+系统合计 | 余量 | 判定       |
| ----------- | ----------------------- | ------------- | ---- | ---------- |
| 10G         | ~14G                    | ~26G          | 6G   | 稳（推荐） |
| 12G         | ~16G                    | ~28G          | 4G   | 上限，可用 |
| 14G         | ~18G                    | ~30G          | 2G   | 危险       |
| 16G         | ~20G                    | ~32G          | 0    | 必崩       |

固定成本：minigames ~4G、skyblock ~4G、Velocity ~1G、系统+MCSM ~3G，合计 12G 打底。

推荐值：

```bash
-Xms10G -Xmx10G    # 推荐，上限锁死，稳定 + 防 OOM
-Xms8G  -Xmx8G     # 保守，给堆外多留余量
```

## 5. 容量量级：内存 vs CPU

蓝条代表纯内存能装的数量，橙条代表 CPU 实际流畅处理的数量——差几个数量级，说明内存从来不是瓶颈。

| 对象          | 10G 内存能装 | CPU 流畅处理       | 瓶颈在              |
| ------------- | ------------ | ------------------ | ------------------- |
| 村民          | ~200 万个    | ~200 个就卡        | CPU（AI / 寻路）    |
| 漏斗/机器方块 | ~1000 万个   | ~2000 个吃紧       | CPU（每 tick 检查） |
| 加载区块      | ~5000 个     | 视距8 约 200 个/人 | CPU / 带宽          |

### 规模对照表

| 规模   | 在线玩家 | 加载区块 | 村民    | 机器/漏斗方块 | 够用的堆          |
| ------ | -------- | -------- | ------- | ------------- | ----------------- |
| 小型   | 1~10     | ~2000    | <100    | <500          | 4G                |
| 中型   | 10~30    | ~6000    | 100~300 | 500~2000      | 8G                |
| 大型   | 30~60    | ~12000   | 300~800 | 2000~5000     | 10~12G            |
| 超大型 | 60+      | >12000   | >800    | >5000         | 12~16G + 深度优化 |

## 6. 堆够不够的客观判断

不看"觉得"，看 gc.log：

```cmd
notepad C:\file\leaf-26.3-Velocity-Multiverse\gc.log
```

看 GC 记录 `xxxM->yyyM(1024M)`：括号内为堆容量，箭头右侧为 GC 后实际留存。

| GC 后留存                | 判定                                 |
| ------------------------ | ------------------------------------ |
| 3~5G                     | 10G 绰绰有余，加堆浪费且 GC 扫得更慢 |
| 长期 8~9G + 频繁 Full GC | 真不够，可加到 12G                   |

## 7. CPU 侧优化（治"村民/机器多卡"）

按收益排序：

| 措施               | 配置位置                                                      | 说明                                                                                                               |
| ------------------ | ------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| 休眠非活跃村民     | `spigot.yml` → `tick-inactive-villagers: false`               | 主力优化，远处村民不 tick AI；只在定时唤醒窗口检查（每 600 tick 唤醒 4 个，持续 100 tick）                         |
| 距离动态 AI（DAB） | `config/leaf-global.yml` → `dab.enabled: true`                | `start-distance: 12`、`max-tick-freq: 20`、`activation-dist-mod: 8`；villager 默认在黑名单（满频 tick）            |
| 控制视距           | `server.properties` → `view-distance` / `simulation-distance` | survival 现为 8 / 6，不要再调高                                                                                    |
| 村民集中管理       | 游戏内                                                        | 交易村民集中到单一区块，清掉散养的                                                                                 |
| 漏斗优化           | `spigot.yml`                                                  | `hopper-transfer: 8`、`hopper-can-load-chunks: false` 已开；`config/leaf-global.yml` → `use-vanilla-hopper: false` |

### DAB 黑名单与村民

- `tick-inactive-villagers: false` 是休眠级优化，比 DAB 降频更狠，两者作用有重叠
- 已关 `tick-inactive-villagers` 后，再把 villager 移出 DAB 黑名单的边际收益很小
- 副作用：铁傀儡塔、繁殖机、村民农场在玩家不常驻的区块会掉效率；交易补货在远处变慢
- 结论：保持 `tick-inactive-villagers: false` + villager 仍在 DAB 黑名单，是最稳组合
